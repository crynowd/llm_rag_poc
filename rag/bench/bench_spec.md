# Benchmark Spec
format_version: 1

Короткое описание: спецификация нормализованных benchmark-кейсов и детерминированных проверок для локального RAG PoC.

## Формат `bench_cases_normalized.jsonl`
Каждая строка содержит JSON-объект:

- `format_version` (int): всегда `1`.
- `case_id` (string): уникальный идентификатор кейса.
- `source_case_id` (string|null):
- `null` для base-case;
- `case_id` базового кейса для paraphrase-case.
- `doc_id` (string): идентификатор документа.
- `query` (string): пользовательский вопрос.
- `expected` (object):
- `type`: `answer` | `not_found`;
- `must_contain`: массив проверяемых якорей;
- `forbidden`: массив запрещенных строк (может быть пустым);
- `requires_inference`: boolean.
- `tags` (array[string]): тематические теги.
- `difficulty` (int): `1 | 2 | 3`.

## Base vs Paraphrase
- Base-case определяется правилом: `source_case_id == null`.
- Paraphrase-case определяется правилом: `source_case_id != null`.
- Определение base/paraphrase не зависит от суффикса `case_id` (`-A`, `-P1`, ...).

## Документы и doc_id
- Ответы могут опираться на любой документ корпуса, если ответ корректен.
- `doc_id` в кейсе используется как диагностика/контекст, но не является жестким ограничением для retrieval.

## Парафразы
- На каждый base-case: 2-4 парафраза.
- Нейтральные русские шаблоны:
- `Уточни: <query>`
- `Кратко: <query>`
- `Подскажи: <query>`
- `В Правилах указано: <query>` (только если не меняет смысл).
- Парафраз не должен добавлять новые факты и ограничения.

## Difficulty и requires_inference
- `difficulty` описывает объем/структурную сложность кейса:
- `1` - простой факт/определение;
- `2` - перечисление, таблица, несколько условий в одном фрагменте;
- `3` - сложный кейс по объему/ограничениям.
- `requires_inference` - отдельный флаг (независим от `difficulty`), указывает, что ответ требует объединения 2+ фактов/цитат.

## Правило для `must_contain`
- Избегать хрупких якорей, зависящих от одной конкретной словоформы (например, только `Российской Федерации`), если в ответах возможны устойчивые варианты (`РФ`, `России`).
- Предпочтение отдавать устойчивым уникальным терминам/подстрокам.
- Рекомендуемый размер `must_contain`: до 6-8 элементов.

## Нормализация чисел при проверках
Для `must_contain` и `numbers_grounded` в скоринге:

- удалять обычные пробелы и неразрывные пробелы внутри чисел;
- аккуратно нормализовать запятую/точку в числах без изменения смысла;
- корректно обрабатывать проценты (не ломать значения вида `0,75%`).

## Дополнительное поле
- `evidence_substring` можно использовать как необязательное поле в будущих/промежуточных артефактах.
- На текущем этапе это поле не является обязательным для `bench_cases_normalized.jsonl`.

## Метрики (детерминированно)
- `not_found_accuracy`
- `citations_present_rate`
- `must_contain_pass_rate`
- `numbers_grounded_rate`
- `retrieval_hit@k` (если retrieval-данные доступны в результатах прогона)

## Прогресс в run_bench
- В терминал выводится одна обновляемая строка прогресса в формате:
`[ 12/250 |  4.8% ] elapsed=00:01:23 eta=00:27:10 case_id=DU-003-P1`
- Обновление происходит минимум раз на кейс (или реже при `--progress_every`), строка перезаписывается через `\r`.

## Дополнительные поля в результатах прогона
В `bench_run_result.jsonl` добавляются поля:
- `timing_ms` (int): длительность обработки кейса в миллисекундах.
- `status` (string): `OK` | `FAIL`.
- `error` (null | object): при ошибке `{ "type": "...", "message": "..." }`, иначе `null`.

## Нормализация NOT_FOUND
- Единое правило: если итоговый ответ обозначен как NOT_FOUND, `is_not_found` должен быть `true`, а `stop_reason` = `not_found`.
- Если `is_not_found=true`, `answer_text` должен начинаться с `- Ответ: NOT_FOUND` (единый формат).

## Принципы quote scoring
- Используется мягкий штраф (soft-penalty) за частотные юридические токены, если их нет среди ключевых слов запроса.
- Учитывается приблизительный IDF на уровне чанка: редкие слова запроса дают больший вклад.
- При равных score предпочтение предложениям с большей coverage (больше уникальных query-слов).

## Изменения формата
При изменении структуры:
1. Обновить этот файл.
2. Добавить/обновить валидацию.
